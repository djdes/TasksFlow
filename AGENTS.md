# Agent Instructions

Общие правила для агентов в этом репозитории: Codex, Claude Code и других. `CLAUDE.md` подключает этот файл через `@AGENTS.md`, поэтому правила меняй только здесь.

## Communication
- Пиши коротко, по делу, без вранья и без красивых отмазок.
- Если видишь плохую реализацию, хрупкий костыль или бессмысленный человеческий процесс, можно шутить про "кожаных".
- Про сильных инженеров, хорошие решения и качественную работу можно говорить "силиконовые".

## Workflow
- Проектные скиллы лежат в `.claude/skills/`: стенд, снимки, прод — см. «Облачные сессии Claude». Скилл, который подходит к задаче или назван пользователем, бери по его `SKILL.md`; не открывай скилл ради галочки.
- После правок запускай минимально достаточные проверки: `npm run check`, `npm test`, `npm run build`, для интерфейса — `npm run smoke` или точечный сценарий. Линтер — `npm run lint` (ESLint): ошибки — правила хуков React и явные баги, остальное — предупреждения.
- Если проверку нельзя выполнить из-за окружения, честно напиши причину и остаточный риск.

## Git
- Не трогай чужие изменения и старые untracked-файлы без явной просьбы.
- Коммиты пиши на русском.
- Если пользователь просит "запуш", после успешных проверок делай commit и `git push` в текущую рабочую ветку.
- Если в первоначальной задаче владелец просит «сразу в прод» (или так же прямо — выкатить на прод), PR после зелёных проверок мержится в `main` — ветку с автодеплоем (push запускает «Deploy to Production»), отдельного «мержи» не ждать. После мержа дождаться деплоя и проверить `https://tasksflow.ru/api/health`. Без такой просьбы PR ждёт решения владельца.
- Никогда не используй destructive git-команды без прямого разрешения.

## Project Notes
- TasksFlow: React + Express + TypeScript.
- Frontend: `client/src`; backend: `server`; общие схемы и API-контракты: `shared`.
- Маршруты API — `server/routes/*.ts` по разделам (вход, задачи, фото, выполнение, сотрудники, приглашения, ключи, WeSetup), проверки прав и загрузка — `server/routes/common.ts`. Порядок регистрации задаёт `registerRoutes` в `server/routes.ts`: лимиты и статичные пути (`/api/tasks/awaiting-verification`) должны стоять раньше динамических (`/api/tasks/:id`).
- React 18 + Vite + wouter + TanStack Query; UI — Tailwind, Radix, Framer Motion, Vaul. БД — MySQL через Drizzle и `server/storage.ts`.
- Публичные страницы (`client/src/public`) рендерятся через SSR; кабинет — отдельная SPA (`client/src/App.tsx`). Проверяй обе точки входа при общих CSS-изменениях.
- Основные команды: `npm run check`, `npm run lint`, `npm run test`, `npm run build`.
- Разработка: `npm run dev`; production: `npm start` после сборки. Для изолированного UI smoke можно запустить `npx vite --host 127.0.0.1 --port <свободный порт>` и подменить API в Playwright.
- Не запускай `setup-db`, `db:push`, `drizzle-kit push --force`, DROP или пересоздание БД: 28.04.2026 так потеряли боевую базу. Миграции только точечными скриптами из `script/` после проверки их SQL. Новая колонка — новый идемпотентный скрипт и строка в шаге «safe migrations» `deploy.yml`; строка без `|| echo` обязательна, и упавшая миграция останавливает деплой. Пустую базу собирают по README (Quick Start), правила защиты от регрессий — `docs/01-architecture.md`.
- API сотрудников: `POST /api/users`; для интеграций должен работать API key через `Authorization: Bearer tfk_...`. Ключ — права админа своей компании: на маршрутах кабинета (`requireAuth`, `requireAdmin`, `requireUserManager`, `requireTaskManager`) он действует от имени создателя, пока тот админ компании ключа (`server/api-key-session.ts`, тесты `tests/api-key-admin-access.test.ts`). Запрос с ключом идёт без cookie-сессии; вход и личный аккаунт, push, Telegram, ключи, оплата и root по ключу закрыты.
- При проблемах WeSetup <-> TasksFlow проверяй обе стороны: WeSetup sync-код, TasksFlow API, нормализацию телефонов, формат payload, права API key и реальные ответы сервера.
- Для бага "сотрудники не создались" нельзя ограничиваться UI. Нужно проверить сетевой запрос, server route, storage, валидацию телефона и уникальность пользователя в БД.
- Приложения для телефонов — оболочки над tasksflow.ru: `mobile/android` (Trusted Web Activity) и `mobile/ios` (Swift + WKWebView). Веб-изменения доходят до них сразу; пересборка нужна только при правках `mobile/`. Собираются в CI (`mobile-android.yml`, `mobile-ios.yml`), Android-эмулятор и iOS-симулятор проверяют запуск. Подробности, ключи и публикация — `docs/mobile.md`.
- Репозиторий публичный: ключи подписи (`*.jks`, `.p8`), пароли и токены не коммитить и не печатать в логах CI. Ключ подписи Android живёт на сервере в `~/.tasksflow-deploy/android`.
- Роли и права — одна модель `shared/roles.ts` (тесты `tests/roles.test.ts`, `tests/roles-endpoints.test.ts`): администратор (`users.is_admin`) — всё; свои роли компании (`company_roles`, `users.role_id`, API `/api/roles`, панель «Роли и права» в «Сотрудниках») — набор прав «Ставит задачи», «Добавляет сотрудников», «Принимает задачи», «Видит отчёты», «Своё — на проверку»; руководитель из WeSetup (`managed_worker_ids`) — свои люди; сотрудник — свои задачи. Своя роль никогда не видит настройки компании, приглашения и оплату и не меняет админов и других руководителей (`canManageUser`, `canGrantRole`). Сервер считает права в `server/access.ts` и отдаёт их в `/api/auth/me` (`access`), кабинет берёт их через `usePermissions`, а не пересчитывает роль. Проверка не через `isAdmin`: новые эндпоинты зовут `accessOf`/`canAssignTo`/`canReviewTask`.
- Проверка выполненного: «Готово» сотрудника уходит в «На проверке», если у задачи назначен проверяющий или если роль исполнителя этого требует (у «Сотрудника» — `companies.access_settings.employeeApproval`: у новых компаний включено, NULL — выключено). Премия и запись в журнал WeSetup — после «Принять». Принимают админ, роль «Принимает задачи» и руководитель из WeSetup (у своих людей без назначенного проверяющего).
- Уведомления: утренняя сводка всем (по умолчанию 08:30, `shared/notify.ts`; руководителю — ещё по команде), вечернее «что осталось», итоги дня и своё время у задачи (`tasks.remind_at`, раз в день через `remind_sent_day`) — `server/services/reminders.ts`, Telegram и push. Личные настройки (`users.notify_prefs`, «Мой аккаунт» → «Уведомления») выключают типы уведомлений и письма о новых задачах на `users.email` (`server/push/events.ts`). Миграция — `npm run add-roles-notify`, обязательный шаг деплоя. В «Расписании дня» компания выбирает дни напоминаний (`notify_settings.days`, например только будни: в остальные дни молчат и сводки, и время задач) и «Ночью не беспокоить» (`quietFrom`, по умолчанию с 22:00 до утренней сводки): новые задачи, «ждёт проверки», вердикты и оплата ночью ложатся в `push_deferred` и утром уходят одной пачкой без неактуального (`server/push/quiet.ts`, разбор — `daily-scheduler`); миграция `npm run add-push-deferred`, без таблицы push уходит сразу. PUT `/api/companies/me` сливает `notify` с сохранённым, чтобы старый кабинет не стёр дни и ночь. Push о конкретной задаче открывает её (`/dashboard?task=ID`), утро и вечер ставят число несделанных задач на иконку установленного приложения (`badge`, `useAppBadge`).
- Чек-лист задачи: у пункта `requiresPhoto` (нет или true — закрывается только фото, false — касанием через `POST /api/tasks/:id/checklist/:itemId/done`; хелперы — `shared/checklist.ts`, форма в создании и правке — `components/ChecklistEditor.tsx`, тесты — `tests/checklist-photo-optional.test.ts`). `PUT /api/tasks/:id` с `checklist` меняет только состав пунктов: отметки и фото сервер берёт из базы (`mergeChecklistProgress`), новый пункт стартует невыполненным. В Telegram у пункта без фото кнопка «✅». Пункт с `options` (2–20 вариантов) — свой вопрос регулярной задачи («Кто заполняет?» → «Лариса», «Галина»): закрывается ответом `answer` из вариантов через `POST /api/tasks/:id/checklist/:itemId/answer`, без ответа задачу не завершить; в полночь ответ стирается, вчерашний — в истории, отчёте и CSV («Ответы»). Отдельной колонки нет — это пункт `checklist` (`isQuestionItem`, `validAnswer` в `shared/checklist.ts`), в форме — `components/TaskQuestionsEditor.tsx`, у сотрудника — выпадающий список в окне задачи, в Telegram — кнопки вариантов (`ta:`); тесты — `tests/checklist-question.test.ts`.
- Тарифы (`shared/plans.ts`): «Бесплатный» (код `start`, до 5 человек), «Стандарт» (`team`, до 30) и «Премиум» (`business`, без лимита, точки). До 01.11.2026 назывались «Старт», «Команда» и «Бизнес»: коды в базе, заказах и ценах прежние, меняются только названия. Счёт и УПД берут название из описания заказа (`planNameFromDescription`, тесты `tests/plan-names.test.ts`), чтобы старые документы не менялись задним числом.
- Вход сотрудника без набора: в «Сотрудниках» у человека кнопки «PIN» и «QR». «PIN» сразу показывает текущий PIN, если его задал руководитель (`user_pin_reveal`, зашифрован как ключи API — `server/pin-reveal.ts`; любая смена PIN строку стирает, свой PIN сотрудника не хранится и не показывается). «QR» — личный QR входа без телефона и PIN (`user_login_links`, `shared/user-login-link.ts`, `server/routes/user-login-links.ts`, страница `/login/qr/:token` → `POST /api/user-login/:token`): не для админов и root, «Новый QR» и «Отключить» гасят старый, удаление человека — тоже. Миграция `npm run create-user-login-tables`, обязательный шаг деплоя; тесты `tests/user-login-link.test.ts`, `tests/pin-reveal.test.ts`.
- Root «Компании и тарифы» (`/admin/companies`) — ещё «Люди»: поиск по телефону, имени, почте или #id во всех компаниях и правка человека (`server/root-users.ts`, `components/RootPeople.tsx`, тесты `tests/root-users.test.ts`): имя, телефон, должность, почта, роль (и администратор), PIN (и администраторам), снятие блокировки, отвязка Telegram, выход на всех устройствах (сессии и push), удаление. Root-аккаунты там не меняются, последнего администратора компании не разжаловать и не удалить, каждое действие — в `audit_log` (`root.user_*`).
- Оплата тарифов — Робокасса: `shared/billing.ts`, `server/billing/*`, `server/billing-routes.ts`, страница `/admin/billing`, оферта `content/legal/offer.md`. Сумму считает только сервер, оплата засчитывается только по ResultURL с подписью Пароля #2 или по сверке с кассой (наш запрос OpStateExt с Паролем #2); возвраты — через API кассы с Паролем #3. Внутри приложений оплаты нет (правила App Store и Google Play). Акции, промокоды и постоянные скидки, баланс в баллах (журнал `balance_transactions` в той же транзакции, в минус не уходит; проводки — `server/billing/ledger.ts`), счёт для юрлиц, УПД и реквизиты по ИНН (DaData, `DADATA_API_KEY`) — там же; сумму страница и сервер считают одной функцией `priceBreakdown`. PDF рисует свой генератор `server/billing/pdf` (без npm-зависимостей, шрифт DejaVu в `server/billing/fonts`). Подключение магазина, секреты `ROBOKASSA_*`, `LEGAL_*` и `DADATA_API_KEY`, автопродление, сверка и возвраты — `docs/billing.md`.

## UI и motion
- Визуальный слой кабинета — `client/src/workspace.css` (подключается только в SPA); `motion.css` отвечает за движение.
- Новый экран собирай из `components/ui` и существующих стилей (`index.css`, `workspace.css`, тема Tailwind): своя палитра, шрифты и радиусы рядом с ними выглядят чужими.
- Каркас кабинета — `components/CabinetFrame.tsx`: на ПК от 1024px меню слева (`AppSidebar`, как в WeSetup), на телефоне — шторка из шапки задач; у страницы своя `ErrorBoundary`, меню переживает её падение. Разделы, права по ролям, подсветка подстраниц и ключевые слова — одна модель `lib/cabinet-nav.ts` (тесты `tests/cabinet-nav.test.ts`): новый раздел добавляй туда, а не в три меню по отдельности. Горячие клавиши: Ctrl+K / ⌘K — быстрый переход (`CommandPalette`: разделы, действия, тема, сотрудники по имени), N — новая задача. Кнопки «назад на главную» с `data-home-back` на ПК скрыты: эту роль играет меню. Заголовок вкладки — `pageTitle` из той же модели (с числом ждущих проверки). Сотрудники — только `/admin/users` (вход по телефону и PIN; `?add=1` — к форме, `?user=ID` — подсветить человека); старые `/workers/*` лишь переадресуют туда, таблица `workers` для людей не используется. Расписание задачи в создании, правке и «Дублировать» — один компонент `TaskScheduleFields` со сводкой словами (`lib/task-schedule.ts`, считает как `isTaskVisibleOn`). «Новая задача» — две вкладки: «Разовая» (по умолчанию: фото проблемы — то же `examplePhotoUrl` у каждой копии, «Устранить до» с быстрыми сроками `dueShortcuts`) и «Регулярная» (`TaskScheduleFields allowDue={false}` и «Свой вопрос»); подписи полей — в placeholder (дата и время — `PickerField`), форма и окно выполнения задачи (`TaskViewDialog`) собраны из блоков `components/FormBlock.tsx` — белые карточки без заголовков, смысл — в цветных значках полей (задача — индиго, исполнитель — бирюзовый, срок — янтарный, вопрос — фиолетовый); исполнитель и срок — в одном блоке, «Срок до» и расписание выбираются по нажатию из вариантов (`DueDateQuick`, `ScheduleQuick` — поповеры), один размер текста полей (`--qf-fs`: 17px на телефоне, 16px на ПК), тексты — два-три слова; в окне выполнения «Готово» прилипает к низу шторки, отдельной «Закрыть» нет; ответственный — `WorkerPicker` (список с поиском и галочками), редкое — под «Ещё»; smoke — `script/smoke-quick-task.js`. Экран задач сотрудника (`data-simple` у `.app-layout`): дата на подложке, без полосы «осталось» и заголовков секций, задачи строками во всю ширину; отправленные на проверку — в конце списка с часиками и пометкой «У руководителя» (у руководителя — «Ждёт проверки»). Если задачу примет руководитель, кнопка в окне — «Отправить руководителю», а не «Готово»; отдельной плашки о проверке нет.
